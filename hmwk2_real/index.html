Caesar cipher vs. toy ECC on secp256k1

Encryption, statistical cryptanalysis, and a key-space attack. Everything runs locally in your browser (BigInt, no libraries).

0. Message

1. Toy ECC scheme (Part 1)

ECIES-style hybrid scheme on secp256k1 (y² = x³ + 7 mod p, generator G, order n). Assumption: if your Part 1 scheme differs, replace the encrypt/decrypt handlers in script.js.

  • Private key d: secret integer, here restricted to 1…2^b.
  • Public key Q = d·G: published.
  • Encrypt: pick ephemeral k, send R = k·G; shared secret S = k·Q; keystream SHA-256(S.x ‖ i); C = M ⊕ keystream.
  • Decrypt: S = d·R = d·k·G = k·Q → same keystream → M = C ⊕ keystream.

Both are “secret-key-in, ciphertext-out” maps, but Caesar’s security is limited by its tiny key space and by leaking plaintext statistics; the ECC scheme leaks no statistics, so its only weakness is the size of the key space (and design details, see §5).



4. Statistical cryptanalysis of Caesar


The model is learned from the first half of the corpus (letter and bigram frequencies, add-one smoothing); tests use the second half, so test texts are unseen. Paste a corpus in another language to retarget the attack. Scores: χ² distance of the decrypted letter histogram from the expected one; bigram negative log-likelihood. For each of the 26 candidate keys (exhaustive search) the lowest score wins.

Effectiveness and limits. With ≳50 letters both scores find the key almost always; below ~10–20 letters the histogram is too noisy and χ² often picks a wrong shift, while bigrams hold up better because they use more evidence per letter. Both need the right language and a representative corpus, and fail on texts with unusual letter use (e.g. lipograms, acronyms). Exhaustive search itself is trivial (26 keys); the statistics are only needed to rank candidates automatically, which a human does by reading.



5. Attack on the restricted ECC key


The attacker knows Q (and R, C). Since d ≤ 2^b, they find d by solving Q = d·G:


    

  • Brute force: compute G, 2G, 3G, … until it equals Q: ≈ 2b additions (capped at b ≤ 18 here).
    • 

  • Baby-step giant-step: with m = 2^⌈b/2⌉, store jG for j < m, then walk Q − i·mG until it hits the table: d = i·m + j. Cost ≈ 2b/2 time and memory.
    • 

  • BSGS on R: if the ephemeral k is also drawn from the small range, k follows from R = k·G, and S = k·Q decrypts without ever finding d.
    • 







Versus the Caesar attack. The Caesar attack is ciphertext-only and statistical: it exploits structure the cipher leaks from the plaintext. The ECC attack uses no plaintext statistics at all, the ciphertext looks random; it is a pure search for the discrete logarithm, and the public key Q acts as a verifier (d·G = Q confirms success), so no language model is needed.


Why it does not scale. For a proper 256-bit d, brute force needs ≈ 2256 steps and even the best generic algorithms (BSGS, Pollard’s rho) need ≈ 2128 group operations: at 1012 operations/s that is ≈ 1019 years, and BSGS would also need ≈ 2128 memory. No sub-exponential attack is known for well-chosen curves. Each extra bit doubles brute force and multiplies BSGS by √2, so the 16 → 256-bit jump is astronomically larger.


Weaknesses beyond the key space (optional). From the restriction: small d and small k (above). From the design: no authentication, so the ciphertext is malleable (flipping a bit of C flips the same plaintext bit); the keystream depends only on S.x (no R/Q in the KDF, no domain separation); no check that R lies on the curve (invalid-curve attacks); a repeated k reuses the keystream, so C₁ ⊕ C₂ = M₁ ⊕ M₂; SHA-256 counter mode is fine for toy use but a real scheme would use a standard KDF plus an AEAD.
