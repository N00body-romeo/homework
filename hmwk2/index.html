Task · check the pipeline

From mnemonic to checksummed address

Mnemonic → BIP-39 → seed → BIP-32 / BIP-44 → private key → secp256k1 → public key → Keccak-256 → address → EIP-55 → checksummed address. Change the phrase, the passphrase or the path and every stage below is recomputed.

Input

Learning tool only. Never type the phrase of a wallet that holds real funds into a web page, and never use a phrase generated here. The test phrase is public: anything sent to its addresses is lost.

Compare with a real wallet

MetaMask, Rabby, Rainbow, Exodus and similar wallets run exactly this pipeline. To see it from the outside:

  1. Use a fresh, empty wallet (or a test profile). Choose "import with a recovery phrase" and enter the test phrase.
  2. The first Ethereum account must be the address in the red box above: 0x9858EfFD…Eda94 for the test phrase.
  3. Add a second account: it is the next address_index (the table in the BIP-32 / BIP-44 section lists the first five).
  4. In a wallet that supports a passphrase (hardware wallets and some software wallets), enter one: a completely different set of addresses appears, with no error.
  5. Wallets show the words (once, at creation), the address, and the private key only on an explicit export. They do not show the seed.

BIP-39 · mnemonic sentence and seed

Words in, 512-bit seed out

Role. BIP-39 turns random bytes into words a person can write down, and turns those words into the seed that the rest of the pipeline starts from. The last bits of the phrase are a checksum, so most typos are caught when the phrase is entered.

1 · entropy (key generation) and its checksum

    


    
2 · seed (key derivation)

    
seed = PBKDF2( password = mnemonic,  salt = "mnemonic" + passphrase,
               PRF = HMAC-SHA512,  iterations = 2048,  length = 64 bytes )

    
    
The 2048 iterations make every guess of a phrase cost 2048 HMAC computations. The passphrase goes into the salt, so a different passphrase gives an unrelated seed and never an error message. The seed does not depend on which language or word list was used, only on the exact text.

  







  

    
BIP-32 and BIP-44 · hierarchical deterministic wallets

    
One seed, a tree of private keys

    
BIP-32 role. One seed produces a whole tree of private keys, so a single backup covers every account ever created. Each node is made from its parent with HMAC-SHA512. BIP-44 role. It fixes what the levels of the tree mean, so a wallet and the next one agree where to look for account number N.

secp256k1 · elliptic-curve public-key cryptography

    
Private key to public key

    
Role. This is the step of HMWK 1 at full size. The private key k is a number below n and the public key is the curve point Q = k·G. Going from k to Q is fast, going back from Q to k is believed to be infeasible, and that one-way relationship is what lets a signature prove ownership of an address without revealing k.


    
curve  y^2 = x^3 + 7 over F_p,   p = 2^256 - 2^32 - 977
G      = (79BE667E...F81798, 483ADA77...D4B8)
n      = order of G, about 1.158 x 10^77 (prime)
Q = k*G, computed by double-and-add

    
private key k

    
    
public key Q = k·G

    
    
encodings of the same point

    
    

    
Same equation as HMWK 1 with a 256-bit prime instead of 17. The toy curve could be solved by trying all 18 points; here the best known generic attacks need about 2¹²⁸ steps. The address uses the 64-byte form (x ‖ y). The 33-byte compressed form is what BIP-32 hashes for normal child keys.

  







  

    
Keccak-256 · hashing

    
Public key to address

    
Role. A hash function squeezes input of any length into a fixed-size digest in a way that cannot be reversed. Ethereum hashes the 64-byte public key (x ‖ y, without the 04 prefix) and keeps the last 20 bytes. The address is therefore a short fingerprint of the public key.


    
input: x ‖ y (64 bytes)

    
    
Keccak-256 (32 bytes): the first 12 are dropped, the last 20 are the address

    

    
Keccak-256 is not SHA3-256

    
Both use the same sponge: the 1600-bit permutation Keccak-f[1600], rate 1088 bits, capacity 512 bits. They differ only in the padding. Keccak, as submitted to the NIST competition, appends the byte 0x01 and then the closing 0x80. The standard SHA-3 (FIPS 202) appends 0x06 first, which carries two extra domain-separation bits. One different input byte gives a completely different digest, so a SHA3-256 library cannot compute Ethereum addresses.

EIP-55 · mixed-case checksum encoding

    
Address to checksummed address

    
Role. A mistyped address sends money to the wrong place and cannot be recalled. EIP-55 adds error detection without changing the address bytes: hash the lowercase hex text with Keccak-256, then write each letter in upper case when the matching hash digit is 8 or more. Software that ignores case still reads the same address, and software that checks case catches typos.

Role and purpose

    
The six pieces and six kinds of operation

    

      
BIP-39
mnemonic sentence and seed
RoleEncodes 128 to 256 bits of entropy plus a checksum as 12 to 24 words, and stretches the phrase into a 512-bit seed.
PurposeA backup a person can write down and check, that works across wallets.

      
BIP-32
hierarchical deterministic keys
RoleDerives a tree of private keys and chain codes from the seed with HMAC-SHA512.
PurposeOne backup for unlimited accounts, and a way to hand out public keys without private keys.

      
BIP-44
derivation paths
RoleGives the levels of the BIP-32 tree a meaning: purpose, coin type (60 for Ethereum), account, change, address index.
PurposeTwo wallets that follow it find the same accounts from the same phrase.

      
secp256k1
elliptic-curve public-key cryptography
RoleTurns a private key k into the public key Q = k·G, and is the curve used to sign transactions (ECDSA).
PurposeA one-way relation between a secret and a public value, so ownership can be proved without revealing the secret.

      
Keccak-256
hash function
RoleHashes the public key, and the lowercase address for EIP-55, into 32 fixed bytes.
PurposeA short, uniform fingerprint of the public key that cannot be inverted.

      
EIP-55
mixed-case checksum encoding
RoleHides a checksum in the capitalisation of the address letters.
PurposeDetects typos and wrong pastes without changing the address format.

EIP-55 sits on the border: the checksum is computed with a hash but is carried by an encoding trick (letter case). The BIP-39 phrase is also mixed: encoding of the entropy, plus a checksum, and the seed derived from it uses key derivation. Key generation happens once, at the very start. Everything after it is deterministic: the same phrase gives the same address on every wallet.

  







  

    
Temporal and historical context

    
Four decades, seven milestones

    
The mathematical tools are old and the wallet standards are young. RSA (1977) and SHA-2 (2001) are 24 years apart, while the other five items, from BIP-32 to EIP-55, all fall in the five years from 2012 to 2016.

    
    
      
  1. 1977
    RSA: public-key cryptography
    The first practical system where encryption and signing use a public and a private key. Ethereum does not use RSA but elliptic curves, which rely on the same idea of a one-way relation between two keys.
    2. 
      
  2. 2001
    SHA-2 / SHA-512
    NIST announces SHA-256, SHA-384 and SHA-512 in 2001 (FIPS 180-2 follows in 2002). Here SHA-256 builds the BIP-39 checksum and SHA-512 sits inside PBKDF2 and HMAC.
    3. 
      
  3. 2012
    BIP-32: hierarchical deterministic wallets
    One seed, a tree of keys. Before it, wallets stored a pool of unrelated random keys and every new key made the backup out of date.
    4. 
      
  4. 2013
    BIP-39: mnemonic code
    Makes the seed writable and checkable as 12 to 24 words.
    5. 
      
  5. 2014
    BIP-44: multi-account hierarchy
    Standard paths: purpose, coin type, account, change, index. Ethereum wallets later reuse it with coin type 60.
    6. 
      
  6. 2015
    SHA-3, based on Keccak
    Keccak won NIST's hash competition in 2012 and FIPS 202 standardised SHA-3 in 2015, with different padding than the original submission. Ethereum had chosen the original Keccak before the standard was final and kept it, which is why Keccak-256 and SHA3-256 differ.
    7. 
      
  7. 2016
    EIP-55: mixed-case checksum addresses
    Typo protection for addresses that needs no change to the address itself.
    8. 
    

    

      public-key cryptography
      hash functions

The order explains the design. The hash functions and public-key cryptography existed first. The wallet standards then built key management on top of them (2012 to 2014), and the Ethereum-specific pieces, Keccak-256 and the checksum, came last. The pipeline reads from the top down in this page and from the oldest primitive to the newest one in the timeline.

Discussion

    
Why not one algorithm for everything?

    
Because no single algorithm has all the properties the pipeline needs, and because the jobs are different. Each step solves one problem and hands plain bytes to the next one.

    

      
PieceProblem it solvesWhat it needsWhy the others cannot do it

      
        
BIP-39, BIP-32, BIP-44
key management		Backing up and organising many keys, and agreeing on where they are.Determinism (the same phrase gives the same keys), a human-sized backup, a fixed tree layout.They are conventions built from SHA-256, HMAC and PBKDF2. A hash alone has no tree and no checksummed words, and the curve alone does not derive keys.

        
secp256k1
public / private		Proving you control an address, signing transactions, with nothing secret shared.An asymmetric pair: public value computed from the private one, not the other way round, with signatures.A hash has no key pair and no way to verify a signature without the secret. This is the only step that needs algebraic structure.

        
Keccak-256
hashing		Reducing a 64-byte public key to a short, uniform, fixed-size identifier.One-way, fixed output, uniform and avalanche behaviour.The curve output has algebraic structure (HMWK 1: only about half of the x values occur, and (n − k)G has the same x as kG). It is not designed to compress or to behave like random bytes.

        
EIP-55
checksum		Catching typos in an address people copy by hand.Error detection with no change to the 20 address bytes.A hash gives the digest but has no place in the address to put it. EIP-55 uses the letter case as free extra bits.

      
    

    
The steps are also separated on purpose. A weak or broken primitive hurts only its own job: the checksum can be wrong without exposing a key, and the hash of the public key is not needed to sign. Using one algorithm for everything would tie all these properties together, and a flaw in it would break everything at once.
